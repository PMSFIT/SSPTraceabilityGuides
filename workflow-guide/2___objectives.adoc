= SSP Traceability Layered Standard – User Guide

This guide explains how to apply the *SSP Traceability Layered Standard* in practice.

It focuses on:

* Structuring simulation information
* Linking artifacts and results
* Enabling traceability and reuse

The standard is defined as an XML schema (STMD) and is intended to be used with appropriate tool support.

For a formal definition, see the specification:
https://modelica.github.io/ssp-ls-traceability/main/

== 1. Introduction

=== 1.1 Purpose of this Guide

This user guide provides:

* Practical explanations
* Usage patterns
* Examples

It complements the specification and focuses on real-world application.

=== 1.2 What SSP Traceability Enables

Using SSP Traceability, you can:

* Structure simulation-related information consistently
* Trace results back to inputs and assumptions
* Reuse simulation setups
* Exchange data across tools and organizations
* Improve collaboration with partners

== 2. Core Concepts

=== 2.1 Credible Simulation Process (CSP)

The *Credible Simulation Process (CSP)* is the foundation of SSP Traceability.

IMPORTANT:
The CSP does not describe a chronological workflow.

Instead, it provides a *logical structure* for organizing simulation information.

Real simulation processes are iterative and recursive.
For traceability, a stable logical structure is required.

**Therefore:**

* **CSP = logical structure of information**
* **NOT = execution timeline**

=== 2.2 Simulation Task Meta Data (STMD)

The *STMD file* is the central element.

It:
- Represents the CSP structure
- Links all relevant artifacts
- Serves as the traceability backbone

Key idea:
- Data remains in existing systems
- STMD contains links and metadata
- Exchange is done via SSP containers

=== 2.3 Three-Layer Model

SSP Traceability can be understood using three layers:

[cols="1,3"]
|===
| Layer | Description

| Process | Logical structuring (CSP)
| Data | Storage, versioning, data management
| Workflow | User interfaces and tool interaction
|===

SSP Traceability mainly addresses the *process layer*.

== 3. Credible Simulation Process in Practice

Each CSP phase consists of:

* Inputs – required information
* Procedure – how it was done
* Outputs – results
* Rationale – why it was done this way

The STMD schema directly maps this structure.

Existing simulation information can be linked accordingly.

== 4. Linking Information

=== 4.1 Basic Principle

Information is linked into the STMD structure based on its role.

[cols="1,2"]
|===
| Type of Information | STMD Location

| Requirements / request | Analysis → Input
| Models / parameters | Implementation
| Results | Output
| Decisions / assumptions | Rationale
|===

=== 4.2 Simulation Request

A simulation request typically contains:

* Administrative information
* Description of the simulation task

Recommended mapping:

[cols="1,2"]
|===
| Content | STMD Location

| Administrative data | Admin phase
| Task description | Analysis → Input
|===

Notes:

* A single file can be linked multiple times
* Information can be split across multiple sources

=== 4.3 Full vs. Lightweight Traceability

Full traceability:

* Link Inputs, Procedure, Outputs, and Rationale

Lightweight traceability:

* Link at least Outputs of each phase

Trade-off:

* Less effort vs. reduced trace depth

=== 4.4 Linking Between Phases

Outputs of one phase are typically used as Inputs for the next phase.

This creates the *traceability chain*.

== 5. File Structure and Packaging

SSP Traceability extends SSP using the `/extra` directory.

Example:

[source]
----
/extra/
  org.ssp-standard.ssp-traceability.stmd/
    simulation.stmd
    linkedFiles/
----

The STMD file:

* Defines the structure
* Contains links to all artifacts

== 6. Metadata

=== 6.1 Purpose

Metadata enables:

* Search
* Filtering
* Reuse

=== 6.2 Storage Options

Metadata can be stored as:

* Classifications (inline)
* Separate SRMD file (Simulation Resource Metadata)
* Attached to linked artifacts

All approaches are equivalent.

=== 6.3 Classification Concept

Metadata is implemented using classifications.

Properties:

* Simple structure
* No hierarchy
* Multiple entries allowed

Example:

[source]
----
execution.tool.name = Dymola
execution.tool.version = 2024x
----

=== 6.4 Structuring Metadata

Since no hierarchy is defined:

* Use naming conventions (e.g. dot notation)
* Use grouping patterns if needed

=== 6.5 Minimum Metadata Set

For basic traceability:

* Project / simulation task
* Model name
* Tool and version
* Input / output references

This already enables:

* Search
* Basic reuse

== 7. Search and Reuse

With minimal metadata, typical questions can be answered:

* Which simulations belong to a project?
* Where was a model used?
* Which tool/version combinations exist?
* Which setups can be reused?

Additional metadata improves analysis capabilities.

== 8. Design Specification with SSP

SSP supports:

* Exchange of simulation models
* Definition of system structures

SSP Traceability extends this by linking:

* Design specifications
* Implementation artifacts
* Simulation results

=== Example

* FMU → model implementation
* SSP → system structure
* STMD → traceability

Result:

Full trace from specification to simulation result.

== 9. Data Exchange and Versioning

=== 9.1 Principle

SSP Traceability:

* Does not replace data management systems
* Enables standardized exchange between them

=== 9.2 Exchange Mechanism

* Data is packaged into an SSP container
* STMD defines:
  - Structure
  - Links
  - Versions

This represents a *snapshot (baseline)*.

=== 9.3 Import and Export

Export:

* Create SSP container
* Include required versions
* Link via STMD

Import:

* Unpack container
* Update or create new versions

=== 9.4 Important Note

SSP containers are:

* Not intended for long-term storage
* Used for data exchange between systems

== 10. Git-Based Workflows

A simple approach:

* Unzip SSP container
* Store structure in Git
* Use Git for versioning

This supports:

* Collaboration
* Transparency
